# The image viewer shipped for months and could not open a picture

The September audit listed Images as one of two apps that never opened: `open_app
name=image-viewer` answered `accepted: true`, no window appeared, and `failed_launches` stayed
empty. The launch was only the surface of it.

## What was wrong

**Nothing routed to the app.** `ROUTES` in `wire/dock.rs` sent `image_viewer` and `images` to
screen 11, the shell's own Images screen. The comment there said why: the standalone binary "had
no arm, so yantrik-image-viewer sat in /opt/yantrik/bin unreachable". So the audit's window never
appeared because no process was ever started — the shell navigated its own screen instead.

**The app could not have shown anything if it had started.** `apps/image-viewer/src/main.rs` read
no command-line argument, published no control surface, and had no file path anywhere in it.
`file_name` was never set by any code path, so the window opened on its empty state and stayed
there. `nav_prev` and `nav_next` logged "Navigate previous image" and returned. Run by hand on the
VM it did open a window — an empty one, which is the whole of what it could do.

**Crop and batch were worse than dead.** A Crop button opened an overlay reading "scaffold — full
crop selection coming soon". A Batch button opened a panel with width and height fields and a
progress bar; the handler behind it spawned a thread that logged `Batch rotate image 3/12`, ticked
the progress bar to completion, and set the status to "Rotated 12 images by 90° (logged)". No file
on disk changed. That is a progress bar for work that never happens, in the shell as well as the
app.

## What changed

**One implementation, in `crates/yantrik-image-core`.** Which files are pictures, which ones sit
beside this one, what the file says about itself. The shell's `wire/image_viewer.rs` and the
standalone app now answer from the same code; the app previously had none of it.

**The app opens pictures.** It takes a path on the command line, claims the single-instance slot,
and a second launch hands its file to the running window instead of opening another one. It
publishes `app-image-viewer` with `open`, `show`, `next`, `previous`, `rotate`, `fit` and
`toggle_info`, and `describe` reports the file, position in the folder, dimensions, rotation and
what the file says about itself — so the audit's own method can exercise it.

**The launcher and Files both reach it.** `images` routes to the program, and double-clicking a
picture in Files launches the app with that path rather than loading it into a shell screen.

**Rotation is applied once.** The component already rotates its own property when its buttons are
pressed and calls the callback to say so; the app's handlers had applied it a second time, which
turns a 90° press into 180°. The handlers are now notifications, and the control-surface actions
set the property directly because no button was pressed in that case. `rotate` answers with
`file_unchanged: true`: turning a picture on screen does not rewrite it, and a caller should not
have to guess that.

**Crop and batch are gone**, from the app, the shell screen and the shared component — buttons,
overlay, panel, progress bar and handlers. Nothing in this OS can rotate or resize a picture on
disk yet. When something can, they come back with it.

**A picture that cannot be shown says so.** A `notice` on the viewer names the file it could not
open, in the app and in the shell's screen, instead of leaving the window blank.

## The layout nobody could see

With the app opening pictures, the window showed one: about 400 pixels wide, in the top corner,
with most of the window empty. Two faults in the shared component, both older than this change
and both invisible while the app could not open a file and the shell's screen was reachable only
by double-clicking a picture in Files.

The container below the header was a `HorizontalLayout`, carrying a comment written for the row
further down ("The content, with the agent rail beside it"). So the zoom toolbar, the separator,
the AI panel and the picture were laid side by side. Making it a `VerticalLayout` stacked them,
and then the agent rail — a sibling of the content row rather than a child of it — sat under the
picture instead of beside it. The rail moved into the row, and the row now takes the height left
over from the header and toolbar, which it never asked for: without that every child kept its
natural size and the picture drew into a small box.

## Verified on VM 520

Deployed to `/opt/yantrik/ui-deployments/images-20260920T153822Z`, originals in its `backup/bin`,
shell restarted with its own environment so labwc, Notes, Terminal and Editor stayed up. Checked
against processes and the compositor rather than against the action's answer, with three real
pictures and one text file named `.png` in `~/Pictures`:

- `open_app name=image-viewer` started a process and the compositor reported an `Images` window.
  That is the audit's test, which used to answer `accepted: true` with no window and nothing in
  `failed_launches`.
- `open` showed the file: `verify-0-aurora.png`, `1 of 4`, `1920 × 1200`, `266.7 KB`, `PNG` —
  dimensions read from the file, not invented.
- `next` moved to the following picture and `previous` came back.
- `rotate direction=right` reported `rotation: 90` with `file_unchanged: true`, and the file's
  SHA-256 on disk was identical before and after.
- The text file named `.png` was named on screen with "Could not open
  /home/yantrik/Pictures/verify-notes.png" rather than a blank window.
- A path that does not exist was refused: "no file at /home/yantrik/Pictures/nothing-here.png".
- A second launch carrying a different picture left one process running and switched the open
  window to that picture.

Screenshot: `design/previews/images-vm-2026-09-20.png`. The test pictures were deleted afterwards
and `~/Pictures` left empty, as it was found.

## Tests

`tests/image-core`, 10 tests, no window: extension matching, a folder listed in name order with
non-pictures excluded, opening one picture selecting that picture rather than the first,
wrap-around navigation, a single-picture folder, selecting within an open folder, the empty
gallery, and file-size formatting.

One of them caught a bug while being written: asking for a file that is not there used to fall
back to the first picture in the folder, so the viewer would show a different image and say
nothing about the one that was requested. It now keeps the requested file selected, which is what
lets the window name what it could not open, with the rest of the folder still reachable.
