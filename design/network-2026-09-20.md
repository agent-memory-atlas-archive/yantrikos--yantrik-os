# The network app called five methods that did not exist, and drew two readings it never took

Network Manager was the largest screen in the fleet — 2506 lines of Slint behind 235 lines of
Rust — and the one the September audit quoted from. "Firewall: Off" went into that audit as a
security finding about this machine. The app had never looked at a firewall in its life.

## What was wrong

**Not one method name in common.** `apps/network-manager/src/main.rs` called `network.wifi_toggle`,
`network.wifi_scan`, `network.wifi_connect`, `network.wifi_disconnect` and `network.wifi_forget`.
`services/network-service/src/main.rs` implemented `network.interfaces`, `network.status` and
`network.dns`, then `_ => Err("Unknown method")`. Every press of every Wi-Fi control returned
"Unknown method". Three of the five — toggle, disconnect, forget — dropped the result into a
`let _ =`, and the toggle then wrote `tracing::info!("Toggle WiFi: {} -> {}")` as though it had
happened. This is Calendar's disease one degree worse: there the two ends disagreed about the
names of parameters, here about the names of the methods.

The source of the app said so, in a comment added when the read half was repaired: *"Not one name
in common, so every button returned 'Unknown method' into a `let _ =` and looked like it had
worked."* The read half was fixed and the write half was left exactly as it was.

**Two readings were fabricated.** `wifi-enabled` (network_manager.slint:223) and
`firewall-enabled` (:251) were `in property <bool> …: false` that Rust never wrote. The screen
drew `root.firewall-enabled ? "{rule-count} rules" : "Off"` in warning colour, and the Wi-Fi rail
line read `!root.wifi-enabled ? "Off" : …`. Both were Slint defaults rendered as measurements.
The test machine is wired with no Wi-Fi adapter at all, so what the window was actually saying —
"Wi-Fi: Off" for hardware that is not in the machine, "Firewall: Off" for a firewall nothing had
asked about — was wrong twice over in the same window.

They were not the only two. The lint counted **34 `in` properties never set from Rust** on this
window, the worst in the fleet: signal strength, IP address, link rate, gateway, subnet, saved
networks, every Bluetooth and VPN and diagnostics list, the firewall rule count, the firewall
backend name, the AI provider table.

**Eighteen dead handlers of twenty-four.** All five Bluetooth callbacks, all three VPN, all four
firewall writes, five diagnostics, and AI explain: each one a `tracing::info!` and a return.

**No control surface at all,** and nowhere on screen for a failure to be said.

## What the machine actually runs

Checked in the build recipes rather than assumed.

**NetworkManager, driven by nmcli.** `deploy/yantrik-os/build-debian-iso.sh` installs
`network-manager` (line 201) and enables the `NetworkManager` unit (line 970);
`deploy/yantrik-os/cloud-init/user-data.yaml` installs the same package (line 119) with a note
saying it was added because nmcli is called from nine places in this codebase and was absent from
every machine until then. `wpasupplicant` is installed as NetworkManager's WPA backend. There is
no `iwd` and no `iwctl` anywhere in the build. So nmcli it is.

**No firewall at all, on an ISO-built machine.** Neither recipe installs `nftables`, `iptables`,
`ufw` or `firewalld`, and the ISO debootstraps `--variant=minbase`, which is priority-required
packages only. A machine built from a distribution cloud image may carry `nft`; an ISO machine
very likely carries nothing. That is precisely why the firewall is detected at runtime, and why
"no firewall tool is installed on this machine" is one of the four answers the app can give.

## What changed

### The contract is a type now, on both ends

`crates/yantrik-ipc-contracts/src/network.rs` carries `method::*` constants for all eleven RPCs,
the request structs (`WifiRadioParams`, `WifiScanParams`, `WifiConnectParams`,
`WifiForgetParams`) and every response type. The response types moved there too:
`NetworkInterfaceInfo`, `NetworkStatus` and `DnsConfig` used to live in the service under a
comment reading "not in contracts yet", and the app took them apart field by field out of a
`serde_json::Value`. A rename cannot land on one end alone; it stops compiling on the other.

Three of the new types exist because a `bool` was the bug:

- `RadioState` is `On | Off | Unknown`, because `wifi-enabled: false` could not say "there is no
  radio here" and so said "off".
- `WifiState` carries `adapter_present` separately from `radio`, and a `reason` for when the
  answer is thin.
- `FirewallStatus` is `Active | Inactive | Absent | Unknown`. `Absent` is "no tool is installed",
  `Inactive` is "a tool looked and found nothing loaded", `Unknown` is "I was not allowed to
  read it" and always carries a reason. Only the middle one is honestly "off".

`rule_count` is `Option<i64>`: `None` for an active firewall whose ruleset this session may not
read, because zero is a number somebody counted.

### The service has the write half

`services/network-service/` gained eight methods — `wifi_state`, `wifi_known`, `firewall`,
`wifi_radio`, `wifi_scan`, `wifi_connect`, `wifi_disconnect`, `wifi_forget` — and two modules
with no I/O in their decision-making: `nmcli.rs` and `firewall.rs`.

**Every write re-reads and answers with what it then saw.** `wifi_radio` runs
`nmcli radio wifi on`, re-reads the state, and *fails* if the radio does not read `on` afterwards.
`wifi_connect` fails if the machine is not joined to the SSID it was asked for, and says which
one it is on instead. `wifi_disconnect` fails if the machine is still joined. `wifi_forget`
re-reads the saved list and fails if the network is still in it. This is Container Manager's
`disagree` pattern: a command that exits zero and did not do what it was asked is a failure too.

**Every failure is classified, in nmcli's own words.** `nmcli` absent, `nmcli` unstartable,
NetworkManager not running, no Wi-Fi adapter, polkit refusal, wrong password, SSID not found,
nmcli's own wait expiring, and anything else passed through verbatim. Each gets its own
JSON-RPC error code, so a caller does not have to read English to tell a missing adapter from a
wrong password.

**Adapter presence is read from the kernel, not from NetworkManager.**
`/sys/class/net/<iface>/wireless` exists for a wireless interface and nothing else. It answers on
a machine where NetworkManager is not running, is not installed, or has the device marked
unmanaged — and "there is no adapter" and "I could not ask" are the two answers that must never
be confused. The conformance probe uses the same test for its ground truth, so the two are
reading the same thing.

**The terse parser handles nmcli's escaping.** `nmcli -t` escapes a `:` inside a value as `\:`
and a backslash as `\\`, and an SSID is free-form: `Cafe: Free` is an ordinary network name.
Splitting on a bare `:` truncates it, and a truncated SSID is one this machine cannot join while
the list on screen looks perfectly reasonable. A hidden network arrives with an empty SSID field
and is reported as hidden rather than dropped, because a row that quietly disappears is how a
list comes to say "no networks in range" when there are some.

### The password

`nmcli device wifi connect <ssid> password <pw>` puts the passphrase in `argv`, where every other
user on the machine can read it out of `/proc/<pid>/cmdline` for as long as the process lives —
and a connect runs for up to twenty-five seconds. The companion's own `wifi_connect` tool does
exactly this today.

So `nmcli::run_with_secret` passes `--ask` and writes the secret to nmcli's stdin. The passphrase
is then in this process's memory, in the pipe, and in NetworkManager's — which is where it has to
end up anyway. `WifiConnectParams` has a hand-written `Debug` that prints `<given>` or `<none>`
instead of the value, so a `{:?}` in a log line, a trace or a hand-built error cannot leak it
either. Nothing echoes it back: not the action result, not `describe`, not the notice, not the
`wifi-connect-status` line on screen. The app clears the password box on both success and
failure — a wrong secret left in a text field gets tried again by accident.

**Residual exposure, stated plainly.** The secret still crosses the app-to-service socket as JSON
in `WifiConnectParams`; that socket is in the session's own runtime directory with the session's
permissions, and it is the same channel every other app call uses. NetworkManager writes the PSK
into `/etc/NetworkManager/system-connections/<name>.nmconnection`, root-readable, because that is
what "save this network" means — the alternative is a machine that cannot rejoin its own network
after a reboot. And `--ask` is nmcli's interactive prompt: if a future nmcli changes what it
prompts for, the line written to stdin would answer a different question. The failure mode there
is a connect that does not work, not a secret in the wrong place, but it is worth knowing.

### The firewall: read it, do not touch it

`firewall.rs` looks for `nft`, then `ufw`, then `firewall-cmd`, and reports what it finds:
which tool, whether it is filtering, how many rules, or why none of that could be determined.

It reads **unprivileged**. `nft list ruleset` and `ufw status` both need `CAP_NET_ADMIN`, which a
desktop session does not have, and the honest answer there is `Unknown` with the tool's own
refusal as the reason — "reading the nftables ruleset needs root and this session is not
privileged: Error: Could not process rule: Operation not permitted". The images built by `deploy/`
do write `yantrik ALL=(ALL) NOPASSWD: ALL` into `/etc/sudoers.d`, so `sudo -n nft list ruleset`
would in fact succeed on them. It is not used. An app that silently becomes root to draw a status
line is a surprise; the reading would be unreproducible on any machine without that sudoers file;
and "I could not read it" is a true and useful thing to say, which is more than the screen was
saying before.

**The four write controls are removed** — toggle, allow port, block port, apply profile. The test
for keeping them was whether this OS has a safe, working privileged path for a desktop app to
change a packet filter. It does not: no polkit rule anywhere in the repo, no setuid helper, no
scoped sudoers entry — only that blanket NOPASSWD line, which is a way to become root for
anything, not a way to be allowed this one thing. Using it so a button press can rewrite the
firewall is a larger decision than this change. What would bring them back: a polkit action and a
small helper with a fixed vocabulary (allow port N, block port N, apply named profile), shipped
in the ISO, with the rule scoped to the desktop session. The note is at the site, in
`network_manager.slint`.

The rule counter is written rather than borrowed on purpose. The companion's `firewall_status`
counts lines beginning with one of six words (`meta`, `tcp`, `udp`, `ip`, `ct`, `iif`) and calls
the answer "~N rules", which misses `oifname`, `icmp`, `jump`, `log`, `counter` and anything
written with a counter first. This one tracks brace depth: a rule is a line inside a chain block
that is not the chain's `type … hook …` declaration. A rule with no verdict word in it — one that
jumps to another chain — is reported as `unknown` rather than guessed at, because a fabricated
ACCEPT in a security display is the same bug one size smaller.

### The app

One function per mutation — `do_radio`, `do_scan`, `do_connect`, `do_disconnect`, `do_forget` —
each returning `Result`, each called by both the button on screen and the control action of the
same name. There is nothing on the person's path that the mind's path skips. `settle()` re-reads
the machine and then writes the command's own verdict into `notice`, in that order, because the
re-read writes the general notice and the command's message is the more specific of the two.

Scanning and connecting run off the UI thread. A rescan sweeps two bands and an association waits
on a WPA handshake and DHCP; the control surface gives an action three seconds before telling the
caller the app did not answer, so both actions declare `.defers()` and their results arrive in
`describe`. The three that can be bounded well under three seconds — radio, disconnect, forget —
run synchronously with `nmcli -w 2`, so nmcli's own timeout produces a readable error instead of
a caller being told the window is stuck.

`serde_json::from_value(v).unwrap_or_default()` is gone. Every call parses into the contract type
and a mismatch is an error the person sees. It cannot happen while both ends build the same
struct; leaving the trap in because it is currently unreachable is how it becomes reachable again.

**Every property the screen renders as a fact is now set from a reading**, and the ones that
cannot be read are set to the value that means unknown: `-1` for the firewall rule count, drawn
as "unknown"; `"unknown"` for the radio; `null` rather than `""` in `describe`, which is System
Monitor's lesson one app over — an empty `cpu_model` and an empty `ip` read to an auditor as
measurements of an empty thing.

### The control surface

Published as `network`, which is what `crates/yantrik-ui/src/wire/dock.rs` routes both `network`
and `network_manager` to (`Launch::Program { id: "network", bin: "yantrik-network-manager" }`).
The socket is `app-network.sock`, beside the service's own `network.sock`; `yos` tries
`app-network` first.

`describe` carries interfaces with addresses, connectivity, DNS, `wifi {adapter_present, device,
radio, connected_ssid, signal, reason, known, in_range}`, `firewall {kind, state, rules, reason}`,
a `source` block saying what each half was read with, and `notice`.

Six actions:

| Action | Grade | Settles | Why |
|---|---|---|---|
| `refresh` | standard | on return | Reads. |
| `wifi_scan` | standard | later | Puts the radio off the air for a few seconds; changes no connection. |
| `wifi_connect` | sensitive | later | Joins a network and hands a secret to whatever answers to that SSID. It does not take the machine off the network it is on: a wired link is untouched and a failed association leaves the previous one standing. |
| `wifi_forget` | sensitive | on return | Destroys a stored credential that may exist nowhere else. |
| `wifi_disconnect` | **dangerous** | on return | |
| `wifi_radio` | **dangerous** | on return | |

The last two are the grading decision worth writing down. The brief offered `sensitive` and asked
whether they deserve worse. They do. The ladder's rule in `control.rs` is "anything that destroys
work or state a person cannot get back". What these destroy is not data, it is the channel: a
caller driving this machine from somewhere else and turning the radio off has cut the wire the
undo would have travelled down. Nothing in this surface can put it back, and no care at the call
site makes it recoverable — it needs someone in the room. `stop` on a container is `sensitive`
because `start` is one call away; there is no such call here. `wifi_radio` carries the grade for
its worst argument, because the ladder grades actions and not argument values, and `off` is the
worst argument.

`wifi_forget` is only *honestly* `sensitive` because the service refuses to forget the network
currently in use. `nmcli connection delete` on the active profile takes the link down as a side
effect, which would have made this a `dangerous` thing wearing a `sensitive` grade. Disconnect
first, deliberately, then forget.

## Tests

`tests/network-core` — 53 tests, `cargo test` in that directory, no nmcli and no firewall on the
machine. Twelve are payload tests over the contract: every method constant, the radio request
carrying a state rather than a flip, a connect with no password not sending the field at all, a
connect with one round-tripping while `{:?}` prints `<given>`, an interface list of the wrong
shape being an *error* rather than an empty list, and `absent`/`inactive`/`unknown` being three
different words on the wire. The rest are captured strings: an SSID with an escaped colon in it,
an SSID with a backslash, a hidden network with an empty SSID, the wired VM's own device list
with no wifi row in it, an unmanaged wireless device still counting as an adapter, nmcli's
sentences for a stopped daemon, absent hardware, a refused secret, an unknown SSID, a polkit
refusal and its own timeout — and, for the firewall, a loaded nftables ruleset, an empty one, one
`Operation not permitted` turns away, ufw active and inactive and root-refused, and firewalld
running and not.

`tests/conformance/probes/network-manager.py` is the live one. It opens the app and asserts a
process, a window and an answering surface — and that the surface answering is the *app's*, since
`yos describe network` falls back to the service's socket and the service publishes a view of its
own with no actions. Then: the interface list and addresses against `ip -j addr`, the nameservers
against `/etc/resolv.conf`, `adapter_present` against `/sys/class/net/*/wireless`, and the
firewall against a reading the probe takes itself with the same three commands at the same
privilege — including the assertion that the app never says `inactive` unless the probe's own
reading says so. `wifi_connect` and `wifi_forget` are asked about a name nothing is called and
must be refused naming either the absent adapter or the name; `wifi_scan` must be refused naming
the adapter. The default route and every address are recorded before and compared after.

## What is NOT verified, and why

**Everything that needs a Wi-Fi adapter.** The test VM is wired and
`/sys/class/net/*/wireless` is empty, so none of this has run against hardware:

- a `wifi_radio on` or `off` that reaches an actual radio, and the re-read that has to agree;
- a `wifi_connect` that succeeds, and the observation that the machine joined the SSID asked for;
- a wrong password, and the app reporting the AP's own refusal — the classifier is tested against
  nmcli's captured sentence, not against a live rejection;
- `--ask`-on-stdin actually satisfying nmcli's prompt. The mechanism is right and the fallback is
  visible (a connect that fails rather than a secret in the wrong place), but no live association
  has been made with it;
- a real rescan, and whether ten seconds is enough on a slow adapter;
- `wifi_disconnect` and `wifi_forget` against a real connection and a real saved network.

**The two `dangerous` actions are not exercised on any machine, by design.** They would cut the
network the probe is running over. That is stated in the probe's own
`notes.sections_not_exercised` in words, because a check that was not exercised and a check that
passed are the same colour from outside and must not be the same word.

**No firewall reading against a live firewall.** Neither build recipe installs one, and the
machines this was written on have none, so the `Absent` path is the only one seen end to end. The
`Active`, `Inactive` and `Unknown` paths are covered by captured output only.

**Nothing was deployed or run.** No VM was available for this change: the service, the app and
the test crate all build (`cargo check` exit 0, no warnings) and the 53 tests pass, but nothing
here has been seen on a screen.

## Lints

Before: 34 unset `in` properties (the worst in the fleet), 19 dead handlers of 24.
After: **0 and 0.** Three `in-out` properties remain unwritten from Rust and are meant to be —

## One owner per domain: what the companion still does beside this

Not changed here — another agent is in that crate — but recorded, because this is the split the
plan wants closed and Network is the next one after Calendar.

`crates/yantrik-companion-tools/src/wifi.rs` has four tools that shell out independently of this
service. `wifi_scan` runs `nmcli device wifi rescan` then `nmcli -t -f SSID,SIGNAL,SECURITY
device wifi list`, splits on a bare `:` (so an SSID containing one is truncated), and falls back
to `iwctl` and `wpa_cli` for backends this OS does not ship. `wifi_status` reads `nmcli -t -f
DEVICE,TYPE,STATE,CONNECTION device status`, greps for the literal string `wifi`, and shells
`sh -c "ip -4 addr show scope global | grep inet"`. `wifi_connect` puts the password in `argv`.
`wifi_disconnect` hardcodes `wlan0` as the device name, so it does nothing on any machine whose
adapter is called `wlp3s0`. All four would be replaced by `network.wifi_scan`,
`network.wifi_state`, `network.wifi_connect` and `network.wifi_disconnect`, and the replacement
fixes the colon bug, the hardcoded interface, the argv exposure and the absent-adapter answer at
the same time.

`crates/yantrik-companion-tools/src/networking.rs` has eight. `network_interfaces` (`ip -br addr`
plus `ip -br link`) is `network.interfaces`. `network_dns` is `network.dns`.
`network_vpn_status` reads `wg show`, `pgrep openvpn`, `nmcli connection show --active` and
`ip -br link show type tun` — no counterpart here, and none is proposed: the VPN tab came off
this app for want of a VPN on the machine. `network_ping`, `network_traceroute`, `network_ports`
(`ss -tlnp`) and `network_diagnose` have no counterpart either, deliberately — see the
diagnostics row above. `network_dns_set` **writes `/etc/resolv.conf` directly** with a `.bak`
beside it; that is a machine-changing network operation living outside this service entirely, and
it is the one in this file that most needs to become a contract method with a grade on it.

`crates/yantrik-companion-tools/src/firewall.rs` has seven, and they are the sharper case.
`firewall_status` and `firewall_list_rules` are graded `Safe` and would be replaced by
`network.firewall` — with the rule count fixed, as above. The other five —
`firewall_allow_port`, `firewall_block_port`, `firewall_block_ip`, `firewall_enable`,
`firewall_disable` — shell `nft` and `iptables` to change the packet filter, including
`firewall_enable` setting `INPUT DROP` policy and `firewall_disable` running `iptables -F`. They
are the same four operations this change just removed from the app's screen for want of a safe
privileged path. They are not removed from the companion by this change, and the asymmetry should
be settled deliberately: either there is a privileged path and the app may have it back, or there
is not and the mind should not have it either.

`crates/yantrik-companion-tools/src/network.rs` is unrelated despite the name — `download_file`,
`http_fetch`, `web_fetch`. No overlap.

## The mind's own network tools — 2026-09-20, later the same day

The section above ends by recording that the companion carried a second implementation of this
domain and that "the asymmetry should be settled deliberately." This is that settlement.
`crates/yantrik-companion-tools/src/{wifi,networking,firewall}.rs` are callers of
`network-service` now, the way commit `19cc631` made the calendar tools callers of
`calendar-service`.

### What the tools were actually doing

Verified by reading them, not assumed from the note above.

**The password was in `argv`.** `wifi_connect` ran `cmd.args(["password", password])`. For the up
to twenty-five seconds an association takes, the passphrase sat in `/proc/<pid>/cmdline`, which
every other user and every other process on the machine can read — `ps` prints it. This is the
exact exposure `nmcli::run_with_secret` was written to avoid on the app side, one crate over,
still open on the side a model can reach.

**`wlan0` was hardcoded** in `wifi_disconnect` and in both non-nmcli branches of `wifi_scan`. On a
machine with predictable interface names — `wlp3s0`, `wlp2s0`, most machines — `nmcli device
disconnect wlan0` fails, and the tool answered "WiFi disconnected." to any zero exit anyway.

**Two of three backends were for an OS this is not.** The file's header claimed `nmcli`, `iwctl`
and `wpa_cli`. There is no `iwd` and no `iwctl` anywhere in either build recipe, and the
`wpa_cli` branch slept two seconds and parsed `scan_results`. Dead code that looked like coverage.

**`nmcli -t` was split on a bare `:`.** Same bug as the app's, same consequence: `Cafe: Free`
became `Cafe`, a network this machine cannot join, in a list that looks perfectly reasonable.

**Nothing re-read anything.** Connect and disconnect each reported the request back on a zero exit.

**`network_dns_set` wrote `/etc/resolv.conf` with `std::fs::write`** and a `.bak` beside it, then
answered "DNS set to 1.1.1.1. Previous config backed up". Both of its outcomes are wrong. A
desktop session cannot write that file, so on an ordinary machine it failed and suggested "Try
running as root"; on the machines `deploy/` builds, where the session can become root for
anything through `yantrik ALL=(ALL) NOPASSWD: ALL`, it would succeed as an unscoped root write
from a tool call. And even as root it does not hold: NetworkManager owns that file and rewrites it
from the active profile on the next carrier change or DHCP renew. The setting had a half-life and
the sentence did not say so.

**The five firewall write tools shelled `nft` and `iptables` directly.** `firewall_enable` set
`iptables -P INPUT DROP` and *then* added the ACCEPT rules one at a time, reporting "Partially
enabled with N errors" if any failed — a window with a DROP policy and no rule letting ssh back
in. `firewall_disable` ran `iptables -F`, flushing every rule on the machine including ones this
OS did not write, under a sentence calling it "disabled". Neither re-read anything.

`network_diagnose` also read `/etc/resolv.conf` itself for a nameserver and ran `iw dev` for the
Wi-Fi line. `iw` is in neither package list, so that line was empty on every machine this OS
builds, and "no adapter" and "no `iw`" looked identical.

### Where the code went, and why not into `yantrik-companion`

The calendar precedent put its backend in `crates/yantrik-companion/src/calendar/backend.rs`
because the calendar tools already lived in the heavy crate. There is no reason to move these:
`yantrik-companion-tools` is the deliberately light crate, and it **already** depends on
`yantrik-ipc-transport` (`app_ui.rs` and `foreign_ui.rs` drive app control surfaces over it).
`yantrik-ipc-contracts` is what `yantrik-ipc-transport` itself depends on and carries nothing but
serde, serde_json and chrono; nothing depends on `yantrik-companion-tools` except
`yantrik-companion`. So there is no cycle and no weight to speak of — one added line in
`Cargo.toml`, naming a crate that was already being compiled. The tools stayed where they were.

`NetworkBackend` lives in `networking.rs`, as `networking::backend`, because all three files speak
it. The fake that stands in for the service in the tests lives beside it under `#[cfg(test)]` and
is shared by all three.

**`wifi_disconnect` and `wifi_radio` are `dangerous`** for the reason already written down for the
app's surface: what they destroy is not data, it is the channel. A mind driving this machine from
somewhere else that turns the radio off has cut the wire the undo would have travelled down, and
nothing in this tool list can put it back. The same verb must not be cheaper because the mind asked
for it rather than a person pressing a button. `wifi_radio` carries the grade for its worst
argument — the ladder grades actions, not argument values.

**`network_dns_set` is `sensitive` and not `dangerous`.** Applying the change re-activates the
connection, so the link drops and comes back with a fresh lease; over ssh that is a visible
interruption. It comes back by itself, which is the line the two above are on the wrong side of.

### The firewall writes: removed, and what would bring them back

The test was the one this document applied to the app: does this OS have a safe, working
privileged path for changing a packet filter? It does not. No polkit action anywhere in the repo,
no setuid helper, no scoped sudoers entry — only `yantrik ALL=(ALL) NOPASSWD: ALL`, written by
`build-debian-iso.sh:294` and `user-data.yaml:28`, which is a way to become root for *anything* and
not a way to be allowed this one thing. The app gave the four equivalent controls up for exactly
this reason on the same day. Keeping them for the mind would have meant the mind may rewrite the
packet filter of a machine it is reached over while the person sitting at it may not — and
`firewall_enable` dropping `INPUT`, or `firewall_disable` flushing the ruleset, over ssh locks out
the owner.

What would bring them back, unchanged from the app's note: a polkit action and a small helper with
a fixed vocabulary (allow port N, block port N, apply named profile), shipped in the ISO, with the
rule scoped to the desktop session — and a method on `network-service` in front of it, so this
domain still has one owner. The note is at the site, in the header of
`crates/yantrik-companion-tools/src/firewall.rs`.

`skills/firewall.yaml` lost the five names with them. A Skill Store card that offers a tool the
registry does not hold is a promise nothing keeps; the card now describes a reading skill, which is
what it is. `skills/networking.yaml` gained `network_diagnose`, which had been registered all along
and was missing from the card — the same inconsistency pointing the other way. The Wi-Fi tools have
no Skill Store manifest at all and never did; they are registered unconditionally by
`register_all`, so nothing lists a name that does not exist, but nothing describes them either.
Left as it is and noted here.

### `network.dns_set`

The twelfth method. `DnsSetParams { servers: Vec<String> }` — a list, not a `primary` and a
`secondary`, because that pair could not express three resolvers and an empty `secondary` meant
both "only one" and "leave the second alone". At most three are accepted: glibc's resolver reads
`MAXNS` = 3 `nameserver` lines, and a fourth would be stored, reported, and never asked anything.
Addresses are parsed as addresses — the tool this replaces checked that every character was a
digit, a dot or a colon, which accepts `...` and `999.999.999.999`.

The service:

1. reads `nmcli -t -f NAME,UUID,TYPE,DEVICE connection show --active`, and `IP4.GATEWAY` per
   device, and picks the active profile whose device holds a gateway — the default route in
   NetworkManager's own words. Loopback is never chosen: NetworkManager manages `lo` as a profile
   of its own on 1.42 and later and nmcli lists it first, and setting resolvers there changes
   nothing while looking exactly like success. With no gateway anywhere, the first non-loopback
   active profile is taken, and the answer names which profile it was either way.
2. `nmcli connection modify uuid <uuid> ipv4.dns "<servers>" ipv4.ignore-auto-dns yes`, and the
   same for `ipv6.*` when an IPv6 server was given. A family with no server in the request is left
   alone. `ignore-auto-dns` is not optional: without it NetworkManager keeps the DHCP servers in
   the list behind the caller's, so a resolver the caller thought it had removed still answers.
   Addressed by `uuid`, never by name — a Wi-Fi profile is named after its SSID, and an SSID may
   begin with a dash or contain a space.
3. `nmcli connection up uuid <uuid>`. Stored is not applied. `nmcli device reapply` would apply the
   change in place without dropping the link and is the gentler instrument, but which properties it
   picks up varies by NetworkManager version and nothing here has run against a live one. `up` is
   the unambiguous one, and the interruption is stated in the tool's own answer.
4. re-reads **both** `/etc/resolv.conf` and `nmcli -t -f IP4.DNS,IP6.DNS device show <dev>`, and
   returns an error if a server that was asked for is in neither. Two readings because they can
   disagree: on a machine with a stub resolver in front, `resolv.conf` says `127.0.0.53` and the
   real servers are only in NetworkManager's view, so a check written against `resolv.conf` alone
   would call a change that worked a failure. Neither machine this OS builds installs
   `systemd-resolved`, so the two agree there — but the check should not depend on that.

**Privilege.** `nmcli connection modify` on a system connection needs polkit's
`org.freedesktop.NetworkManager.settings.modify.system`. Debian's NetworkManager grants it without
a prompt to members of `sudo` and `netdev`, and the `yantrik` user is created in `sudo` by both
recipes (`build-debian-iso.sh:287`, `user-data.yaml:26`), so on the machines this OS builds it
should go through unprivileged. That is read from Debian's documentation and from the recipes, not
run: **it has not been executed against a live NetworkManager.** A refusal is not silent either
way — nmcli says "not authorized", and `nmcli::classify` already turns that into
`PermissionDenied`, which reaches the model as "this session is not allowed to change networking:
…" in nmcli's own words. `lxpolkit` is the agent installed to answer a prompt if one is raised.

### Tests

`tests/network-core` — **66**, up from 53, `cargo test --offline` exit 0. The thirteen new ones
cover the method constant, the request shape, a result whose two readings disagree, the profile
chooser (default route wins; loopback never; a profile with no device never; nothing up at all), an
active-connection row for a connection named `Cafe: Free`, one named `-h`, and NetworkManager's
per-device resolver list. One of them found a real bug while being written: `parse_device_dns`
split IPv6 addresses on their own colons and reported `2606:4700:4700::1111` as `2606` — a resolver
this machine cannot ask, reported as the one it was told to use. It joins the tail back now, and is
tested both escaped and bare.

`crates/yantrik-companion-tools` — **26** new tests across `wifi`, `networking` and `firewall`; 45
in the crate, `cargo test --lib` exit 0. All run against the fake backend; none needs nmcli, an
adapter or a firewall. They assert the things that used to be assumed: that a machine with no
adapter is told apart from a radio that is off, that the interface name is never `wlan0`, that the
password does not appear in the answer and does appear on the wire, that an empty password field is
"no password" and not "the password is empty", that an SSID containing `&` is no longer refused now
that no command line is being built, that a hidden network keeps its row, that a scan which found
nothing is a different sentence from a scan that failed, that `wifi_radio` refuses to guess which
way to flip, that a disconnect which did not take is a failure, that an active firewall with an
unreadable ruleset gets no rule number, and that the firewall registry holds exactly two names.

`cargo check --offline --profile fast -p yantrik-companion-tools -p yantrik-companion -p
network-service` — exit 0, no warnings from these crates. `-p yantrik-network-manager` — exit 0;
the contract change is additive and the app was checked because it shares the contract.
