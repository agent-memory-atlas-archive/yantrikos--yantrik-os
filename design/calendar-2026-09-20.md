# The calendar could not keep an appointment, and said it had

The September audit's worst single finding was `add_event` fabricating success: the action
answered `{"added": "audit", "on": "2026-09-17 23:45"}` and the event did not exist, on that day
or any other. This is what was actually wrong, which turned out to be four faults stacked so
that each hid the next.

## What was wrong

**The service was never running.** `calendar`, `email` and `notes` are registered with
`autostart: false` (`crates/yantrik-ui/src/main.rs`), and the machine rail renders a stopped
non-autostart service as "on demand". Nothing implemented on demand. There is no socket
activation and no path from an app to `ServiceManager::start`, so on a freshly booted machine
the calendar's socket did not exist and every call an app made to it failed at connect.

**The app and the service disagreed about the wire.** Listing asked for `start` and `end`; the
service required `start_date` and `end_date` and rejected the request. Deleting sent `event_id`;
the service read `id`. Both files looked correct on their own page, and
`yantrik-ipc-contracts` only carried the data types, so nothing made the two ends agree. The
listing bug is why the calendar could not show an event even once one was stored: on a machine
with the service running and events on disk, the month came back empty.

**Errors were discarded at every layer.** `on_save_event` called the service inside
`if ... .is_ok()` with no else, then closed the form either way. `on_delete_event` did the same.
The store's `delete` ignored the result of `remove_file`, so removing an event that was never
there reported success.

**The action reported an outcome it never observed.** `add_event` invoked the window's save
callback and immediately returned `{"added": ...}`, describing what it had asked for rather than
what happened. With the three faults above underneath it, that is the fabricated success the
audit saw.

There was also a latent fifth: the app built an event's end time as `hour + 1`, so anything from
23:00 produced `T24:30:00`, which is not a time.

## How it was proved, before it was changed

On VM 520, with the shipped binaries:

- With the service down, `add_event` answered success; `~/.local/share/yantrik/calendar/` did not
  exist and `describe` still reported `events_this_month: 0`.
- Started `calendar-service` by hand, called it directly over its socket: create wrote the file,
  list returned it. The service was never the problem.
- Repeated the action with the service up: still fabricated success, and the service log recorded
  no call — the transport's circuit breaker was holding a verdict from the failed calls the app
  made at startup.
- Restarted the app with the service already up: the event was stored, and the app still showed
  `events_this_month: 0` and `days_with_events: []`, which is the listing parameter mismatch.

## What changed

**The wire is a type now.** `yantrik_ipc_contracts::calendar` carries `method` names and
`EventsParams`, `CreateEventParams`, `UpdateEventParams` and `DeleteEventParams`. The app builds
them and the service parses them, so a rename cannot land on one end alone; it stops compiling on
the other.

**"On demand" is a mechanism.** The shell publishes `start_service` on its control surface
(standard grade), backed by the same `ServiceManager` the machine rail reads, and
`yantrik_app_runtime::service::ensure` asks for the service it needs before calling it. Apps do
not spawn service binaries themselves: if they did, the rail would report "on demand" for a
process that is running, which is the same lie pointing the other way. `SyncRpcClient::clear_breaker`
drops the breaker for an address the caller has just started, or the first call after a successful
start fails against a socket that is already listening.

**Failures are said out loud.** `CalendarScreen` gained a `notice` strip. A save that fails leaves
the form open, holding what was typed, with the reason above it; a delete that fails says so; the
notice is in the app's `describe` too, so a mind reads the same failure a person sees. `add_event`
stores the event first and answers with the id it was stored under.

**The store refuses what it cannot keep.** Empty titles, unparseable times, an end before its
start, and deleting or updating something that is not there are all errors now rather than quiet
successes. The app clamps a late event to `23:59` instead of inventing `24:30`.

## Verified on VM 520

Deployed to `/opt/yantrik/ui-deployments/calendar-20260920T141422Z`, with the replaced binaries
kept in its `backup/bin`. Only the shell was restarted, using the environment read from the
running process, so labwc (72690), Notes, Terminal and Editor stayed up; the new shell is 168750.

Checked against the store on disk and the app's own `describe`, never against the action's answer
alone, and starting from a machine with the service down and nothing stored:

- `add_event` on a cold machine: the service was started on demand (process and socket both
  present afterwards), the event was written, and the action answered with the id it was stored
  under. `describe` moved to `events_this_month: 1` with day 24 in `days_with_events` — the first
  time the app has been able to show an event it stored.
- The event was still listed after the app was killed and reopened, which is the listing path the
  parameter mismatch used to break.
- With `calendar-service` renamed away, `add_event` was **refused** — "could not ask the desktop
  to start the calendar service: Binary not found" — nothing was written, and the reason appeared
  on screen in the app's notice as well as in the caller's error.
- A 23:30 event stored an end of `2026-09-26T23:59:00`. The old arithmetic would have built
  `T24:30:00`, which the store now refuses outright.
- Event times read `14:00 – 15:00` rather than `14:00:00 - 15:00:00`.

Screenshot: `design/previews/calendar-vm-2026-09-20.png`. The test events were deleted afterwards
and the machine left with an empty calendar and the service stopped, which is how it was found.

## Found on the way, not fixed

This machine has two calendars. The Calendar app and the control surface use
`calendar-service`, which stores one JSON file per event under
`~/.local/share/yantrik/calendar/`. The built-in companion's own tools
(`calendar_create_event` and friends, `crates/yantrik-companion/src/tools/calendar.rs`) are
local-first into a SQLite `calendar_events` table, with optional Google sync. Neither reads the
other. So "put it on my calendar", asked of the companion, lands somewhere the Calendar app will
never show, and an appointment made in the app is invisible to the mind's own tools. An attached
mind driving the app through `os_act` does reach the right store, which is why this did not show
up in the audit. Picking one store is a larger change than this one and belongs to whoever takes
the email/calendar sync work next.

## Tests

`tests/calendar-core` (18 tests, run with `cargo test` in that directory) covers the store's rules
without a socket or a desktop: the round trip from create to list, month boundaries including an
event spanning the first of a month, ordering, persistence across a restart, and every refusal
above. Three of them are payload tests — they serialize what the app sends and parse it the way
the service parses it, which is the drift that made the calendar blind.
