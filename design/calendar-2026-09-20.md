# The calendar could not keep an appointment, and said it had

The September audit's worst single finding was `add_event` fabricating success: the action
answered `{"added": "audit", "on": "2026-09-17 23:45"}` and the event did not exist, on that day
or any other. This is what was actually wrong, which turned out to be four faults stacked so
that each hid the next.

## What was wrong

**The service was never running.** `calendar`, `email` and `notes` are registered with
`autostart: false` (`crates/yantrik-ui/src/main.rs`), and the machine rail renders a stopped
non-autostart service as "on demand". Nothing implemented on demand. There is no socket
activation and no path from an app to `ServiceManager::start`, so on a freshly booted machine
the calendar's socket did not exist and every call an app made to it failed at connect.

**The app and the service disagreed about the wire.** Listing asked for `start` and `end`; the
service required `start_date` and `end_date` and rejected the request. Deleting sent `event_id`;
the service read `id`. Both files looked correct on their own page, and
`yantrik-ipc-contracts` only carried the data types, so nothing made the two ends agree. The
listing bug is why the calendar could not show an event even once one was stored: on a machine
with the service running and events on disk, the month came back empty.

**Errors were discarded at every layer.** `on_save_event` called the service inside
`if ... .is_ok()` with no else, then closed the form either way. `on_delete_event` did the same.
The store's `delete` ignored the result of `remove_file`, so removing an event that was never
there reported success.

**The action reported an outcome it never observed.** `add_event` invoked the window's save
callback and immediately returned `{"added": ...}`, describing what it had asked for rather than
what happened. With the three faults above underneath it, that is the fabricated success the
audit saw.

There was also a latent fifth: the app built an event's end time as `hour + 1`, so anything from
23:00 produced `T24:30:00`, which is not a time.

## How it was proved, before it was changed

On VM 520, with the shipped binaries:

- With the service down, `add_event` answered success; `~/.local/share/yantrik/calendar/` did not
  exist and `describe` still reported `events_this_month: 0`.
- Started `calendar-service` by hand, called it directly over its socket: create wrote the file,
  list returned it. The service was never the problem.
- Repeated the action with the service up: still fabricated success, and the service log recorded
  no call — the transport's circuit breaker was holding a verdict from the failed calls the app
  made at startup.
- Restarted the app with the service already up: the event was stored, and the app still showed
  `events_this_month: 0` and `days_with_events: []`, which is the listing parameter mismatch.

## What changed

**The wire is a type now.** `yantrik_ipc_contracts::calendar` carries `method` names and
`EventsParams`, `CreateEventParams`, `UpdateEventParams` and `DeleteEventParams`. The app builds
them and the service parses them, so a rename cannot land on one end alone; it stops compiling on
the other.

**"On demand" is a mechanism.** The shell publishes `start_service` on its control surface
(standard grade), backed by the same `ServiceManager` the machine rail reads, and
`yantrik_app_runtime::service::ensure` asks for the service it needs before calling it. Apps do
not spawn service binaries themselves: if they did, the rail would report "on demand" for a
process that is running, which is the same lie pointing the other way. `SyncRpcClient::clear_breaker`
drops the breaker for an address the caller has just started, or the first call after a successful
start fails against a socket that is already listening.

**Failures are said out loud.** `CalendarScreen` gained a `notice` strip. A save that fails leaves
the form open, holding what was typed, with the reason above it; a delete that fails says so; the
notice is in the app's `describe` too, so a mind reads the same failure a person sees. `add_event`
stores the event first and answers with the id it was stored under.

**The store refuses what it cannot keep.** Empty titles, unparseable times, an end before its
start, and deleting or updating something that is not there are all errors now rather than quiet
successes. The app clamps a late event to `23:59` instead of inventing `24:30`.

## Verified on VM 520

Deployed to `/opt/yantrik/ui-deployments/calendar-20260920T141422Z`, with the replaced binaries
kept in its `backup/bin`. Only the shell was restarted, using the environment read from the
running process, so labwc (72690), Notes, Terminal and Editor stayed up; the new shell is 168750.

Checked against the store on disk and the app's own `describe`, never against the action's answer
alone, and starting from a machine with the service down and nothing stored:

- `add_event` on a cold machine: the service was started on demand (process and socket both
  present afterwards), the event was written, and the action answered with the id it was stored
  under. `describe` moved to `events_this_month: 1` with day 24 in `days_with_events` — the first
  time the app has been able to show an event it stored.
- The event was still listed after the app was killed and reopened, which is the listing path the
  parameter mismatch used to break.
- With `calendar-service` renamed away, `add_event` was **refused** — "could not ask the desktop
  to start the calendar service: Binary not found" — nothing was written, and the reason appeared
  on screen in the app's notice as well as in the caller's error.
- A 23:30 event stored an end of `2026-09-26T23:59:00`. The old arithmetic would have built
  `T24:30:00`, which the store now refuses outright.
- Event times read `14:00 – 15:00` rather than `14:00:00 - 15:00:00`.

Screenshot: `design/previews/calendar-vm-2026-09-20.png`. The test events were deleted afterwards
and the machine left with an empty calendar and the service stopped, which is how it was found.

## The second calendar, found on the way and now closed

This machine had two. The Calendar app and the control surface used `calendar-service`, one JSON
file per event under `~/.local/share/yantrik/calendar/`. The built-in companion's own tools
(`calendar_create_event` and friends, `crates/yantrik-companion/src/tools/calendar.rs`) were
local-first into a SQLite `calendar_events` table, with optional Google sync. Neither read the
other. So "put it on my calendar", asked of the companion, landed somewhere the Calendar app would
never show, and an appointment made in the app was invisible to the mind's own tools. An attached
mind driving the app through `os_act` did reach the right store, which is why this did not show up
in the audit.

**One owner per domain.** `calendar-service` owns calendar data. The companion's five calendar
tools are callers now, built on a `CalendarBackend` trait whose real implementation is the
service's own contract — the typed parameters from `yantrik_ipc_contracts::calendar`, never
hand-written keys, because hand-written keys are what made the calendar blind in the first place.
There is no private store left to fall back to, so a create that fails is a failure the person is
told about rather than a row written somewhere nobody looks.

**Starting the service from inside the shell.** An app is a separate process and asks the shell
over `app.act start_service`, which the shell dispatches onto its Slint event loop. The companion
is not a separate process: it runs on a worker thread in the shell, a few frames from the
ServiceManager itself, and that round trip would leave the process only to come back in and queue
behind whatever the compositor is doing. So `ensure` moved from `yantrik_app_runtime::service` —
which pulls in Slint, and a mind should not link a widget toolkit to keep an appointment — into
`yantrik_ipc_transport::service`, and grew one hook: a process that owns the manager installs it
with `set_local_starter` and `ensure` uses it in place of the socket. The hook calls `status`
before `start`, the same order the control surface uses, so a service whose process has died is
reaped rather than reported as running. The app-facing API is unchanged;
`yantrik_app_runtime::service` re-exports the same three functions.

The shell installs it in `main` before `AppContext::init` rather than after, which is the one
reordering this needed: `init` starts the companion on its own thread, and the first thing that
thread does about the calendar is the migration below, which needs a way to start a service. As
it stood, the manager and the control surface both came into being after the companion did, and
whether the migration could reach either was a race.

Calling `app.act start_service` from the companion's worker thread would not have deadlocked —
nothing on the Slint thread blocks waiting on that worker; the bridge's blocking `ask` and `tool`
are only called from the companion RPC thread, and voice and Telegram each have their own. It is
simply two more ways to fail for nothing.

**The contract grew, modestly.** `CreateEventParams` gained `is_all_day` and `attendees`, both
defaulting, both with a home the stored `CalendarEvent` already had — the mind's tool accepted
`all_day` long before the service could store it, so an all-day appointment asked for by the mind
was kept as a timed one. `UpdateEventParams` gained the same two and `remote_id`. Two methods are
new: `calendar.get_event`, because a caller about to change or remove an event has to know whether
it came from somewhere else, and `calendar.upsert_remote`, which stores an event under the id it
has on the calendar it came from. An argument with no home — `reminders`, `recurrence` — is
reported as NOT STORED rather than accepted and dropped, which is the same fabrication one size
smaller.

**Google sync writes through the service.** A synced event is now a file in
`~/.local/share/yantrik/calendar/` like any other, and the Calendar app shows it; `upsert_remote`
keyed on Google's own id makes a second sync an edit rather than a duplicate. Two things it does
not do, and they are in the module's own comments as well as here. **A meeting cancelled in
Google's web UI is not removed from this machine** — doing that honestly needs Google's sync
tokens, so that "not in this answer" can be told from "not in this page of this answer", and the
old code's version of it was a range delete that took every local event in the window with it.
**One page, one window**: the listing asks for at most 100 events and does not follow
`nextPageToken`, as it always has. With no OAuth2 account configured the whole sync path is a
quiet no-op, as it was before.

**The old rows were carried across, once.** On companion start, any event in the SQLite table
marked `source = 'local'` — or carrying the `local_` id prefix that predates that column — is
created in the service and recorded in `calendar_migrated_events`. The marker is per row, so a
second start moves nothing twice and a service that was down when the shell started is simply
tried again; the SQLite rows are not deleted, because a marker is enough to say they moved and
losing an appointment is worse than leaving an inert row behind. Nothing lists events from that
table any more. What is left of the companion's database on this subject is one row in
`calendar_sync_state` holding the instant of the last successful Google pull, and the dormant
`calendar_events` table the migration reads.

`meeting_prep` used to read that table directly, which is why it could not see a meeting put on
the calendar by the app. It asks the service now, and only when the service is already listening:
a playbook is evaluated every think cycle, and a background loop that starts a service because it
ran is a side effect nobody asked for. It also reports the real number of minutes until a meeting
rather than the flat `30` it used to answer for everything it found.

## Tests

`tests/calendar-core` (69 tests, run with `cargo test` in that directory) covers the store's rules
without a socket or a desktop: the round trip from create to list, month boundaries including an
event spanning the first of a month, ordering, persistence across a restart, and every refusal
above. Three of them are payload tests — they serialize what the app sends and parse it the way
the service parses it, which is the drift that made the calendar blind. The later ones are about
there being one calendar: syncing the same remote event twice stores it once, a remote event that
changed is edited rather than duplicated, an edit does not orphan an event from the calendar it
came from, and attendees, a location and an all-day flag survive a restart of the service. The
last twenty are about the two gaps closed below: the revision token moving on every write and on
no read, resolving a title and a date to exactly one event or to a refusal that carries its
candidates, and what a move is allowed to leave alone — the length an appointment already runs for,
and an all-day event's absence of a clock.

In the companion crate (`cargo test -p yantrik-companion --lib calendar`, 36 tests) the tools are
tested against a calendar that is not a socket: a fake that can be told to refuse. What is checked
there is mostly what a refusal does — a create the calendar refuses is reported as a failure
carrying the calendar's own reason, a calendar that cannot be read is said out loud rather than
answered as an empty day, and deleting or updating something that is not there is an error. Plus
the two the migration turns on: a second start moves nothing twice, and a migration the calendar
refused marks nothing and is tried again with the rows still there.

`tests/conformance/probes/one-calendar.py` is the live one, and it is not a probe of one app. It
makes an event with the mind's `calendar_create_event` and looks for it in the store on disk and in
the Calendar app's `describe`; makes one with the app's `add_event` and looks for it in the mind's
`calendar_list_events` and `calendar_today`; deletes with the mind's tool and checks the app stops
showing it; and checks that the service was started on demand by the tool that needed it. The
mind's tools are reached over `companion.sock` — `companion.tool {name, args}` runs one by name
with no language model in the loop — and the helper for that socket is `lib.companion_tool`, moved
there when the calendar probe became its second caller.

## A mind could put something on this calendar and could not take it off

The surface published `select_day`, `show_month`, `go_to_today`, `add_event` and `set_view`.
Deleting was a Slint callback taking a row index, reachable only from the window — so the
conformance probe could not reach the data-loss bug fixed above it, and recorded the delete path as
NOT EXERCISED with the reason. The contract has had `calendar.update_event` since this document was
written and nothing on the surface could change an appointment at all: a meeting put on the
calendar at the wrong time had to be destroyed and made again.

`delete_event` and `update_event` close both. They take the id the store gave the event, which
`add_event` has always answered with and which `describe` now carries for every event it lists — in
the month, the week and the day, because an event a caller can see and cannot name is one it can
read about and not act on. `delete_event` also takes a `title` and a `date` together, for the
instruction a person actually gives. **Two events of one name on one day is a refusal**, listing
both with their ids and their times, never a guess: picking one removes the wrong appointment half
the time and reports success, which is the trash-icon bug rebuilt one layer up.

`delete_event` is graded `sensitive` and the reason is that there is no trash. The file is the
event; nothing on this machine keeps a copy, so an appointment a person or a mind put there is gone
and its hour with it. It stays below `dangerous` because it destroys one named thing the caller
asked for by name — the range delete Google sync used to do, which took every local event in the
window with it, is what the other grade is for. `update_event` is `standard`, the same as
`add_event`, and the difference is what survives: a moved meeting is still on the calendar under
the same id, the person can see where it went, and this same action puts it back. Moving one keeps
how long it already runs, because "move the standup to 10:00" says nothing about length and an
update that reset it to the default hour would be changing something nobody asked about.

Both go through one path with the trash icon and the window, and both read the store back after
the write rather than trusting the reply. A delete reads the event first so its answer can name
what was removed, and reads again afterwards, because "the service did not refuse" and "the event
is gone" are different sentences — and a service that has gone away answers a read with an error
too, so `-32602` (the store refusing an id it does not have) is told apart from `-32000` (the
question not arriving). `add_event` also grew `duration_min` and `all_day`: the form has no
duration field and the template path has minutes, so the only caller that could say how long a
thing runs was the one that could not, and `is_all_day` has been in the contract with nothing on
the surface able to set it.

## The window follows the store now

The app re-read the store only when the date range on screen changed. That was right while it was
the only writer and stopped being right the day this machine got one calendar with several: an
event the mind created through its own tools, one Google sync pulled in, or one a second caller
added through this same surface did not appear in an open Calendar until somebody navigated away
and back. `one-calendar.py` stepped a month forward and back before every read to get past it,
which is a probe measuring the app's cache and saying so in a comment.

**A cheap question, not a fast poll.** `calendar.revision` is new on the contract and additive:
the event count and the newest modification time under the store directory, a `stat` per file and
no parse. Both halves are needed — the count alone misses an edit in place, the time alone misses a
create and a delete that land inside one filesystem tick — and the directory's own time is in the
maximum because adding or removing an event touches the directory rather than any surviving file.
Reading it never changes it, which is what makes it safe to ask repeatedly, and `tests/calendar-core`
holds that to it: it moves on create, on update and on delete, and not on a listing, a get, a
refused write, or another ask.

The window asks it in two places. **Before every `describe`**, because a mind reads `describe`
immediately after acting and that is exactly the moment a month read several navigations ago lies;
it is one round trip to a local socket, about a millisecond, well inside the three seconds
`control.rs` gives an action on the UI thread, and the month is re-listed only when the answer says
it moved. And **on a twenty-second timer**, for the window nobody is asking about — skipped
entirely while the window is not visible or is minimized, and never starting the calendar service,
because a window sitting idle must not be the reason a service comes up. That is the same rule
`meeting_prep` follows on the companion's side. Idle cost with the window open is one round trip
every twenty seconds and no model replaced when nothing changed; hidden, it is nothing at all.
Focus was considered as the trigger instead and there is nothing to hang it on — this Slint
version has no window-focus callback, so "on focus" would be a poll for focus, which is the timer
already written.

The timer is returned from `wire` and held by `main`. A Slint timer stops when it is dropped, and
`let _keep = ...` inside the function that starts it is how System Monitor came to take one reading
of the machine and show it for the life of the window (b291cb2).

`one-calendar.py` no longer navigates before reading. It asserts the honest thing instead: an
event the mind creates or deletes behind an open window is on screen within five seconds, with the
bound written down in the file and derived from the check before `describe` — a wait that settled
between five and about twenty-five seconds would mean the timer answered and that check had
stopped working. `probes/calendar.py`'s delete section is no longer a note: two events on one day,
the one asked for removed by id and the other still in the store on disk, an ambiguous title
refused with its candidates, an unknown id refused, and an event moved by `update_event` with the
file on disk agreeing about where it went.
