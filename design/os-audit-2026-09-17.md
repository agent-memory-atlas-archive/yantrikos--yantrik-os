# OS-AUDIT.md — the shell's screens, the OS features, honesty under failure, idle cost

Audited 2026-09-17/18 (~22:44–23:20 local), from inside the machine, as a follow-up to
`APPS.md` (the 16 apps — not repeated here). Scope: the 15 shell screens, the OS-level
features (DND, lock, updater, notifications, files, settings), what the machine says when
things fail, and what idle costs.

**Method.** `yos` is not on this session's PATH; every command below is
`/opt/yantrik/bin/yos …` (worked). Screen content read two ways: `yos describe shell --full`
(state JSON) and the a11y service's tree of the shell window (`rpc.py a11y a11y.describe`,
helper: `scratch/screen_probe.py`; full dumps in `scratch/screen-*.{json,a11y.json}`).
Claims cross-checked against `/proc`, `/sys`, the SQLite stores, the event log and
`/opt/yantrik/logs/yantrik-os.log`. Nothing deleted (except the throwaway file the
grade-test itself consumed), no email, no lock, every changed setting set back.

**Memory screen caveats** (verified): there are **two** memory stores. The shared mind
server (127.0.0.1:7440, per CLAUDE.md) keeps its data in
`~/.local/share/yantrik-mind/mind.db` — **17** rows (all `semantic`). The screen instead
counts the shell's own `/opt/yantrik/data/memory.db` (from `/opt/yantrik/config.yaml`
`yantrikdb.db_path`) — 215 rows and growing (+7 during my session). So the number is
true, but it is *not* the shared mind memory, and the recent entries are auto-filler:
the five newest were four copies of "Connected to network 'Wired connection 1'" and an
hourly CPU/network summary. Recall ("Type a query above and Yantrik will recall") cannot
work end-to-end: the configured LLM backend `http://localhost:8341/v1` refuses
connections (verified), and the shell's own log says `Suppressing EXECUTE urges — LLM
offline` every think cycle. **Suspected** (no programmatic path to test search): query
returns nothing or errors.

**Empty/fake/placeholder roll-up:** no screen shows *fabricated placeholder* content.
Empty-but-honest: notifications, images, media, personality (partly). Showing falsehoods:
**about (uptime), system (WiFi; empty Used/Cached/Free values)**. Shallow/unverifiable:
permissions scan counts. Contradictory: bond (days vs streak). Related describe-level
falsehood: `companion_online: false` while the shell's own log emits
`yantrik_companion::proactive` lines every 60 s — the companion is running in-process.

## Part 2 — OS features

### 2.1 do-not-disturb — partial (real toggle, no persistence, nothing to suppress)

```
yos act shell set_do_not_disturb on=true
→ accepted: True, settled: True, {"do_not_disturb": true}
```
State flips; a **"DND" chip appears in the status bar** (a11y element, verified);
`describe` reports `do_not_disturb: true`. But:

- `grep dnd ~/.config/yantrik/settings.yaml` → `dnd_mode: false` **immediately after the
  settled toggle, and again 3 s later** — the toggle never persists (contrast `pin_app`,
  2.4 below, which wrote settings.yaml instantly). A shell restart silently drops DND.
- **Does it suppress anything? Untestable — nothing ever arrives.** The centre was empty
  before, during and after (revision `6500961fa6cd12ab` unchanged across all probes);
  there is no DBus daemon (2.4) and the notifications socket has no post/notify method
  (eight guesses all → `Unknown method`, honest errors). DND guards an empty room.

Set back to `false` afterwards (verified in describe). **Would do:** persist `dnd_mode`
in the same write path `pin_app` uses; and once notifications work, retest suppression.

### 2.2 lock — claims verified, not executed

- Surface: `act: lock() [sensitive, settles on return]`; binary string: **"Lock the
  session"**.
- A lock screen **exists** as a real built-in screen: `yantrik-ui` binary contains
  `' HomeOnboardingLock screenBond screenPersona'` (screen list incl. "Lock screen"),
  `'Enter password to unlockPress Enter to unlock'`, `'wrong PIN'`,
  `'Screen locked' / 'Screen unlocked'`, `is_unlocked`. Verified by artifact inspection;
  I did not invoke it (per instructions).
- `settings.yaml` sets `auto_lock_secs: 300`, yet the 9-hour log contains **zero**
  lock/unlock events, including hours with no user interaction — **suspected** inert
  auto-lock (cannot confirm without leaving the machine idle 5+ min and watching, which
  this session's format doesn't allow; also my probing may reset the idle timer).
- Note: `lock()` is graded `sensitive` and this session's settings ceiling is
  `tool_permission: sensitive` — i.e. a mind at the documented ceiling **can** lock the
  session. Given the CLI bypass in 3.3, that's mostly moot, but the MCP ceiling
  ("standard", per its refusal text) would block it. The ceiling story is inconsistent.

**Would do:** make auto-lock either work or not exist in settings; align the three
ceiling declarations (`settings.yaml tool_permission`, `config.yaml tools.max_permission`,
`YOS_MCP_MAX_PERMISSION` default).

### 2.3 the updater — works (both paths, both channels, real server)

Shell surface (`check_update`, graded safe):
```
yos act shell check_update channel=nightly
→ ["Checking channel 'nightly' on releases.yantrikos.com",
   "installed: v0.1.0-179-g6fc8b13 (6fc8b13)",
   "channel:   v0.1.0-179-g6fc8b13 (6fc8b13)", "up to date"]
  up_to_date: true
yos act shell check_update channel=stable
→ "channel: 474ef21", "update available: 6fc8b13 → 474ef21", update_available: true
```
CLI:
```
/opt/yantrik/bin/yantrik-update check            (default stable) → rc 10
  installed: v0.1.0-179-g6fc8b13 (6fc8b13) / channel: 474ef21 / update available
/opt/yantrik/bin/yantrik-update check --channel nightly → rc 0 / up to date
```
**Is it right?** Yes, as far as observable:
- `releases.yantrikos.com` resolves to **192.168.4.28** — a real server on the LAN; the
  check genuinely asks it (verified via DNS; I did not fetch beyond what the tool did).
- The two independent code paths agree on both channels, and the installed hash
  `6fc8b13` matches the About screen's build. rc encodes the answer (0/10) — honest.
- Blemish: About brands the same commit **"0.3.0"** while the updater reports
  **"v0.1.0-179-g6fc8b13"** — two version stories for one build (git tag base never
  bumped, or marketing number hardcoded). Confusing but not false.
- Did not run `apply_update` (dangerous grade; and see 3.3 — the CLI would have let me).

**Would do:** reconcile the version strings; keep rc semantics.

### 2.4 notifications — broken (three layers deep), and the UI hides it

Sequence of evidence (times local):
1. `notify-send "audit-dnd-off" "posted with DND off"` → **rc 0**. Centre: `count: 0`,
   revision **unchanged**. Nothing arrived.
2. DBus probes: `GetNameOwner org.freedesktop.Notifications` → `":1.11"` (twice, ~22:52);
   one minute later every call fails: `"Could not get … ':1.11': no such name"`,
   `"The name org.freedesktop.Notifications was not provided by any .service files"`.
   Three more rounds 2 s apart: consistently **no owner**. It never came back.
3. The shell's log, at boot (13:55), explains the design:
   `WARN yantrik_os::dbus_notif: D-Bus notification daemon failed to start —
   notifications from other apps will not appear. Is another notification daemon (dunst,
   mako) already running? error=name already taken on the bus`
4. The rival: **`mako` (pid 754)**, started at boot before the shell. It **was** :1.11.
   mako is still alive (state S, up 9.2 h, 8 fds) but no longer owns the bus name — its
   registration died during my session (~1–2 min after my first notify-send; **suspected**
   correlation, unprovable). The shell never re-races for the name.
5. Second `notify-send` after the name was gone → **rc 0 again** (tool-side silent
   "success" — Debian's, not Yantrik's, but it compounds the illusion). Centre still 0.
6. The notifications socket accepts only `dismiss`/`dismiss_all` — there is **no
   sanctioned way to post** into the centre at all.

So: external notifications can never reach the centre (shell daemon disabled at boot by
design-after-defeat; the daemon that won the race then lost its bus name); internally
nothing was ever observed to post either; and the UI says **"All caught up. System
notifications will appear here."** — a friendly empty state that conceals a permanently
broken pipeline. The only honest trace is one WARN line in a 6 100-line log.

**Would do:** retry `RequestName` when the holder disappears (NameOwnerChanged watch);
surface daemon status in the notifications screen ("no notification daemon — external
notifications will not appear"); consider killing/owning mako in the session start-up so
there is exactly one daemon; make `describe notifications` report `daemon: none`.

### 2.5 file browser — works (list, open, show real content)

```
yos act shell files_go path=/home/yantrik/inside-report
→ entries 44 (scratch/, a11y-*.json, APPS.md …) — matches ls exactly
yos act shell files_open name=APPS.md
→ {"opened": "APPS.md", "screen": "editor"}; describe editor:
   name APPS.md, chars 21751, lines 344, modified false;
   content head == `head -c 120` of the file on disk, byte-identical
```
Also exercised `files_go` into `scratch/` (45 entries, real). **Verified.**

### 2.6 settings — change, persist, set back

No action exists to set wallpaper/theme (no `set_*` in the 23-action surface; `a11y.act`
is dead per APPS.md), so the testable settings are the state-backed ones:

- **`pin_app` persists — verified.** `pin_app name=weather pinned=true` →
  `settings.yaml pinned_apps` gained `- weather` within seconds; unpinned → file back to
  the original six entries. Round-trip clean.
- **`set_do_not_disturb` does not persist — verified** (2.1): state true, file false.
- So settings persistence works in general and is **specifically broken for DND**.

**Would do:** route `dnd_mode` through the same settings writer as `pinned_apps`; add a
`set_setting`-style action (or revive a11y.act) so the settings *screen* is reachable by
the minds at all — today every row it displays is read-only to everything but a mouse.

## Part 3 — honesty under failure

The five required probes, exact machine words (all via `/opt/yantrik/bin/yos`):

1. **Missing required argument** — `yos act shell show_screen` (no `screen=`), rc 1:
   ```
   yos: shell.app.act refused: `show_screen` needs argument `screen`
   ```
   Same quality for `files_go` ("needs argument `path`"). **Good.**
2. **App that is not running** — text-editor (no process, no socket), rc 1:
   ```
   yos: no socket for 'text-editor' (try: yos ls)
   ```
   **Good** — though it can't distinguish "not running" from "has no surface at all".
   Bonus: `open_app name=no-such-app` → `refused: no app 'no-such-app' on this machine;
   it can open: terminal, browser, files, …` (full valid list). **Good.**
3. **Refused by grade** — my ceiling per `settings.yaml tool_permission: sensitive`;
   `files_delete` is graded `dangerous`. Throwaway file created first.
   - **MCP path (`os_act`): model refusal** —
     `refused: shell.files_delete is graded dangerous, above this session's standard
     ceiling, so it was not run. An action at that level needs a person to authorise it
     directly — raise YOS_MCP_MAX_PERMISSION if that is the intent.`
     File verified still on disk. Names action, grade, ceiling, reason, remedy. **Good.**
   - **Raw CLI/socket path: NO enforcement — the delete ran.**
     `yos act shell files_delete name=grade-test.txt` → `accepted: True, settled: True,
     {"deleted": "grade-test.txt"}`; entries 45→44; file gone. **Bad — the worst
     honesty/enforcement finding of this audit.** CLAUDE.md's promise ("the refusal
     happens in the OS, not in your judgement") holds only for MCP callers; any uid-1000
     process with the socket — including any mind's bash tool — can run `dangerous`
     actions ungraded. (`apply_update` would have been equally reachable; I did not
     touch it.)
4. **File that does not exist, via the files screen** — rc 1:
   ```
   yos: shell.app.act refused: nothing called `DOES-NOT-EXIST.md` in /home/yantrik/inside-report
   ```
   **Good** — names the file and the directory searched.
5. **`yos describe` on a nonexistent surface** — rc 1:
   ```
   yos: no socket for 'no-such-app' (try: yos ls)
   ```
   **Good.**

Bonus probes:
- Invalid enum: `show_screen screen=bogus_name` → `refused: no screen called
  'bogus_name'; there is: desktop, bond, personality, memory, settings, files,
  notifications, system, images, editor, media, about, packages, devices, permissions`
  — turns the error into documentation. **Good.**
- Socket-level unknown method → proper JSON-RPC `-32601 "Unknown method: post"`. **Good.**
- **Silent DOA (lies):** `open_app name=image_viewer` → `accepted: True, settled: False,
  {"launching": "image_viewer"}`. After 8 s and after 33 s: no process, no window, and
  **`failed_launches: []`** — the failure is never recorded anywhere observable. All that
  really happens is the shell switches to its built-in (empty) `images` screen. Same
  class of lie APPS.md found for the app binaries; the launcher's bookkeeping promises
  (`failed_launches`) stay empty. **Bad.**
- **notify-send rc 0 with no daemon** (2.4) — accepted-true-nothing-happens, from the
  toolchain the OS ships/recommends. **Bad.**

Net: the *error-message* layer is excellent — specific, true, remedial, correct exit
codes. The *outcome-reporting* layer lies by omission where it matters most: launches
that never happen and a grade ceiling that isn't there on the raw socket.

**Would do:** enforce grades in the socket server (per-peer ceiling, e.g. from
SO_PEERCRED + config), not in the MCP shim; populate `failed_launches` when a launched
pid never appears / a launch degrades to a screen switch; make `open_app` for
screen-backed "apps" say so (`{"showed_screen": "images"}`) instead of `"launching"`.

## Part 4 — cost of doing nothing

Method: 60.1 s window, no other commands issued, per-process `utime+stime` deltas from
`/proc/<pid>/stat` (field 14+15, parsed after the comm paren), RSS = stat field 24 ×
page size; system-wide from `/proc/stat` deltas. Script: `scratch/idle_cost.py`.
4 cores (Xeon E5-2660 v2 vCPUs). My own session runs in `foot`+sshd (verified via ppid
chains), **not** inside the measured yantrik-terminal.

**System-wide "idle" CPU: 52.7 %.** Yantrik stack: 41 processes, CPU-sum **1.94 cores**,
RSS-sum **4 025 MB** of 7.8 GB.

| pid | process | cpu % of one core | RSS MB | note |
|---|---|---|---|---|
| 20704 | **yantrik-terminal** | **135–137** | 162 | at an empty `$` prompt — its own surface says last command `echo audit` (previous audit), exit 0. Busy-loop; re-measured over a second window: 137.1 % |
| 701 | **labwc** (compositor) | **45** | 130 | re-measured: 45.3 % — half a core to composite a static desktop |
| 757 | yantrik-ui (shell) | 6.1 | 388 | think cycle every 60 s + observer writes every ~9 s |
| 50269 | yantrik-weather | 3.7 | 179 | idle polling |
| 49889 | yantrik-network-manager | 1.6 | 169 | |
| 49594 | yantrik-container-manager | 1.1 | 165 | |
| 11779 | hermes gateway | 1.1 | 190 | the attached mind — cheapest of the burners |
| 695 | yantrik-mind | 0.4 | 62 | |
| — | 12 more yantrik-* app windows | ~0.0 each | ~170–190 **each** | email, calendar, notes, downloads, music, spreadsheet, sysmonitor, presentation, yDoc, snippets, network, containers — every one parked at ~0 % CPU but ~175 MB RSS |
| — | chromium (browser + gpu + renderers) | 0.1 | 317+114+193+74 | left open from before; untouched per rules |

Context from the event log: the shell's own observer has logged `CpuPressure
usage_percent ≈ 51–57` every ~9 s all day (19 744 rows since boot) — the machine has
**never** been idle; the status-bar "CPU 51 %" I saw on every screen was this. The shell
also runs a Think cycle every 60 s that generates urges and then logs
`Suppressing EXECUTE urges — LLM offline` (backend :8341 dead) — cognition work spent
every minute to produce nothing.

**Who burns CPU while nothing happens:** `yantrik-terminal` (1.37 cores — 67 % of the
stack's burn — for rendering nothing), `labwc` (0.45 cores), then the shell itself and
the weather app. **How much:** ~2.1 of 4 cores, ~53 %, continuously; plus ~4 GB RSS
held by 41 mostly-idle processes, 14 GUI apps costing ~175 MB each to show nothing.

**Would do:** strace/fix the terminal's poll loop first (single biggest win: −34 % of
total machine CPU); investigate labwc's frame loop (no damage-based sleeping?); gate the
think cycle on LLM reachability instead of running it into `Suppressing … offline` every
minute; consider lazy-launching the 12 parked app windows (~2 GB RSS back).
